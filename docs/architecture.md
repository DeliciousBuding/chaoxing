# Architecture

Chaoxing runs as one Go binary. `serve` owns one upstream client, authenticated cookie jar and cache per account, and exposes two loopback listeners. The public listener serves the owner Web UI, OAuth and MCP; the private listener serves local bearer-token calls. Local CLI clients use the default account's daemon session rather than create a fresh upstream client each time.

```text
Browser owner   -> HTTPS mcp.example.com -> Cloudflare Tunnel
                                      -> 127.0.0.1:8792 -> Web UI session -> /api tools
MCP client      -> HTTPS mcp.example.com -> Cloudflare Tunnel
                                      -> 127.0.0.1:8792 -> owner OAuth -> MCP tools
Local CLI client -> chaoxing call
                                      -> 127.0.0.1:8793 -> local bearer -> same tools
                                                                         |
                                                        bounded upstream client
                                                                         |
                                                              Chaoxing over HTTPS
```

Only port 8792 enters the tunnel. Port 8793 is private to the host; it carries authenticated local calls, not public OAuth or browser traffic. `configure` writes private installation state. `query` directly uses the upstream client and is useful for isolated diagnostics; it should not run concurrently against state owned by `serve`.

Several optional layers are off by default. An egress pool (`internal/egress`) routes upstream traffic through configured SOCKS5 endpoints with account-sticky selection, transport-failure cooldown and a direct fallback while the selected endpoint cools; it learns health only from real request outcomes and never probes in the background. An account assignment is stable across restarts and is removed only when that endpoint is no longer configured. When proxies, activity capture or private location presets are enabled, `internal/statestore` persists endpoint health, sticky assignments, sanitized captures and per-account BD-09 location presets/bindings in SQLite. Additional accounts mount under `/t/<id>/` with independent sealed credentials, cookie jars, caches, query queues and OAuth state. The process-wide transport pool, endpoint-health database and outbound budget are deliberately shared; they contain no account session or coursework credentials. This is logical account isolation within one trusted process, not process or network-egress isolation.

Upstream requests also pass a per-account pacing boundary. The default minimum interval is 650 ms with 35% random jitter; redirects and retries use the same boundary. Shared HTTP transports enable HTTP/2, keep at most two idle connections per host, and let Go's transport negotiate gzip automatically when the upstream supports it. The watcher adds randomized 750 ms–3 s gaps between class polls and 5–25 s before automatic sign-in. These values are risk controls, not throughput controls.

## Owner Web UI

`internal/webui` embeds the production Vite bundle from `web/src` and mounts it at `/` and `/app`. It is a separate operator identity from MCP OAuth: login verifies the same owner PBKDF2-SHA256 hash, then issues a random opaque session ID that exists only as a SHA-256 key in memory. The cookie uses the `__Host-` prefix, `Secure`, `HttpOnly`, `SameSite=Strict`, an eight-hour absolute TTL and a thirty-minute idle TTL. The in-memory session is bound to the originating client network: IPv4 `/24` and IPv6 `/64`. This tolerates small mobile-network changes while bounding cross-network cookie theft. All browser API requests must carry the configured Host; a different Host is rejected before authentication. Only trusted reverse proxies may supply the client address. The default trust set is loopback only; `X-Forwarded-For` is read right-to-left from the first non-trusted address, so a direct client cannot forge its leftmost value. Login prunes expired sessions and caps active sessions at 32. Every state-changing API request requires both the cookie and an `X-Chaoxing-CSRF` header matching a separate CSRF cookie. Login attempts are bounded per client network to five per minute and twenty per fifteen minutes. The authenticated dashboard exposes only safe egress, process and watcher counters; public `/healthz` exposes aggregate process/watcher timing and counters without account IDs. Immutable embedded assets are served with strong content-hash ETags, `Vary: Accept-Encoding`, immutable cache policy and precompressed gzip representations.

The UI API has no parallel capability definition. `/api/tools/call` only accepts names from `internal/operation`, and execution is dispatched to the selected root or tenant account executor. API bodies are capped at 128 KiB, tool calls receive a ninety-second context, and errors use safe fault codes. The static bundle has a strict CSP, `nosniff`, no-referrer, HSTS, a restrictive `Permissions-Policy`, `Cross-Origin-Opener-Policy: same-origin`, `frame-ancestors 'none'`, and immutable caching for hashed assets. The bundle contains no analytics or tracker. Its default connections are same-origin only; when the optional Baidu map page is enabled, CSP additionally allows the Baidu GL script/tile origins, while map geocoding calls remain server-proxied and bounded.

The UI intentionally does not expose arbitrary file browsing, shell execution, URL fetching, raw cookies, hidden form values or upstream HTML. Dangerous operations such as final submission and sign-in remain explicit button actions with confirmation.

## Production activity capture

Watcher capture is an evidence layer for still-unverified classroom H5 protocols, especially practice/type-42 flows. Each observation is deduplicated by account and `course:class:activity`, and stores activity identity, state, first/last-seen timestamps, update count and sanitized JSON projections. A practice page can be fetched once through `get_activity_page`; page evidence is never overwritten. The Web UI lists captures without page payloads and fetches sanitized page JSON only through an explicit opt-in query. The store rejects oversized payloads, omits hidden values, cookies, credentials and raw bodies, and prunes entries after a configurable retention period (default seven days). Capture failures do not interrupt watcher operation.

## Concurrency and resource budgets

The smallest stateful unit is an account. Its upstream operations are serialized because login, cookie snapshots and caches mutate together. Allowing concurrent reads against those structures would require a larger state redesign and could produce redundant logins or lost cookie updates. Different accounts can progress independently. Capability discovery does not access account state and bypasses the account queue.

| Boundary | Active / waiting | Saturation behavior |
| --- | --- | --- |
| Account operations, shared by CLI and MCP | 1 / 8 per account | Immediate `RATE_LIMITED` once all nine places are occupied; waiting respects caller cancellation |
| Process-wide outbound HTTP, all accounts | 4 / 32 | Bounded admission, with capacity held through body EOF or close; failures and cancellation release capacity |
| Public MCP transport, per endpoint | 4 / 0 | HTTP 503 with `Retry-After`; this protects request parsing, not account state |

Local calls have a 90-second total budget; MCP tools have 30 seconds. Account and outbound waits consume that same budget, not a fresh timeout per stage. The shared gate has no worker goroutines or polling. Account waiters acquire no outbound slot until they actually issue HTTP, so one busy account cannot reserve the process-wide budget while idle in its queue. There is no strict weighted fairness guarantee. All-tenant overload remains bounded, not unlimited goroutine accumulation inside business queues.

The HTTP transport is shared, not the cookie jar. Raw reads retain the same allowlisted paths and bounded response sizes. Caller cancellation is not classified as a failing proxy. Endpoint persistence is serialized per endpoint but happens outside the pool selection/status mutex; slow SQLite cannot hold that global lock. A persistence error keeps in-memory health usable and sets `persistence_degraded` in private management status.

## SQLite scope and durability

SQLite stores non-authoritative endpoint health, sticky egress assignments, sanitized activity captures and private BD-09 location presets/course bindings—not accounts, assignments, tokens or cookies. One reusable connection serializes short indexed upserts and deletes. This workload does not justify separate reader pools, sharding, a write-behind queue or another service. Healthy rows are deleted; normal requests that do not change health do not write. Replaced endpoints can leave stale rows, which are ignored unless their exact endpoint key is configured again.

The store uses WAL with `synchronous=NORMAL`, a one-second busy timeout, a two-second operation context and a bounded two-megabyte page cache (`cache_size=-2048`). Automatic checkpointing starts at 256 pages; `journal_size_limit=4 MiB` limits retained journal size after resets, not an absolute WAL file-size cap. Schema creation, shape validation and `user_version` update commit atomically. Schema v4 adds proxy assignments, activity captures and location tables; older databases migrate in place and no OAuth reauthorization is required. NORMAL can lose recent health/capture updates on power failure; this is acceptable for reconstructible operational evidence, not an authorization-store policy.

The DB is created/chmodded to 0600 before sidecars, database symlinks are rejected, and filenames are URI-escaped. Existing parent permissions and trusted exclusive ownership still matter. Keep one daemon per store on a local filesystem. Do not copy a live WAL main file as a consistent backup; use SQLite's backup API or stop the owner first. Benchmarks in `internal/statestore` are synthetic local-write measurements, not upstream throughput or deployment capacity claims.

## Authentication boundaries

Public DCR registrations last 90 days so connector setup retries can reuse their cached client IDs. Registration alone grants no permission: every authorization requires owner login and consent. The pool is capped at 128 and reclaims the oldest unapproved registration first at capacity; approved registrations are not evicted by anonymous registrations. Login/consent challenges still expire after 10 minutes and authorization codes after 60 seconds.

The public owner authorization layer supports seven OAuth scopes: `chaoxing.read` for course reads, `chaoxing.sign` for sign-in, `chaoxing.work` for local draft edits, `chaoxing.answer` for generated answers and rapid-answer participation, `chaoxing.work.submit` for upstream work save/submit, `chaoxing.upload` for pan uploads, and `chaoxing.face` for face enrollment/signing. Its password uses a salted PBKDF2-SHA256 hash with 600,000 iterations. This owner credential is separate from the upstream credential, which must be recoverable for automatic login. Use different passwords. Registration records the requested scope, authorization requires explicit owner consent, refresh can narrow but never widen it, and the MCP adapter checks the required scope before contacting upstream or opening the draft store.

Authorization codes expire after 60 seconds and use S256 PKCE. Random opaque access tokens last 15 minutes; refresh families have a 30-day lifetime. Refresh rotation preserves the original expiry. Issuer-bound MAC proofs authenticate family/counter/nonce values so old replay can revoke a family without retaining every historical token. State stores only active digests and one bounded record per family. The authorization server is database-free and does not issue JWTs or publish JWKS. DCR is the default registration flow; optional CIMD requires explicit opt-in and external metadata reachability.

The upstream client implements the upstream AES login protocol over HTTPS. Its GET helper detects login responses, reauthenticates once and retries once. A second login rejection returns `AUTH_REQUIRED`; notices and schedules have their own POST rejection handling after establishing a session with a read. This is not an unlimited retry loop or a verification bypass.

AES-GCM protects upstream credentials and persisted cookies with separate authenticated purposes. A separately stored key is required for unattended operation. Restrict the key and state to the service's trusted identity (root-only for a root-run installation). Root and a compromised service process can recover the credentials; file encryption does not defeat those actors.

## Data boundaries

`internal/operation` is the single transport-independent capability registry. It declares stable operation IDs, legacy MCP names, argument bounds, schemas and descriptions. CLI, daemon and MCP use the same validator and additive result metadata. Business commands call the daemon rather than create another authenticated client. No adapter executes another adapter as a subprocess.

`chaoxing capabilities` and `chaoxing schema assignments.list` work without credentials. `get_capabilities` advertises verified operations and explicitly unsupported domains. The registry is hand-curated from verified behavior, not generated from a claimed official upstream OpenAPI specification.

`meta.status` describes source coverage, not whether homework is finished. Coverage is independent of output pagination. Unknown submission states are never classified as submitted. Aggregation is bounded and retains source failures; notification prose is untrusted data, not instructions or automatically inferred assignments.

Tools read coursework, generate answers, submit explicitly allowlisted sign-in/answer/work/upload actions, or edit local answer drafts. Login and token issuance change authentication state; sign-in changes attendance state and therefore requires `chaoxing.sign`; answer generation/participation requires `chaoxing.answer`; draft mutation changes only local draft state and requires `chaoxing.work` (therefore `answer_work` requires both); upstream work mutation requires `chaoxing.work.submit`; upload requires `chaoxing.upload`; face state requires `chaoxing.face`, and face sign also requires `chaoxing.sign`. Tool allowlisting is enforced at the interfaces; clients do not supply arbitrary upstream URLs or remote commands.

Without a course filter, assignment enumeration uses the incomplete global feed. A course-name query enumerates matching enrolled classes, obtains work-list signatures, pages each class's work list and checks unique rows against upstream totals. `complete: true` is scoped to those matched classes and requires every scan to agree with its total. Output pagination and status filtering then slice the fetched source. Consumers must retain `complete`, `coverage` and timestamp fields. [Tool contracts](tools.md) describes bounds and remaining limits.

The MCP callback has a shared 30-second context. Sequential scans across multiple matching classes may exhaust it before completing; use a narrower course name when possible.

## Optional activity watcher

`internal/watch` is an opt-in background loop inside `serve`. It calls the same activity-read boundary, which uses the shared account queue and bounded outbound budget, then sends alerts through operator-configured senders in `internal/notify`. Per-class schedules and the global window bound polling; interval jitter avoids a fixed request cadence. When `group_activities` is enabled, the same upstream client reads Easemob course-group history and merges `att_chat_course` sign-in cards with the class activity feed by `course_id:class_id:activity_id`. With `auto_sign`, the watcher calls the upstream sign-in state machine once for each new normal/location activity. If private location bindings are enabled, it resolves the current schedule-specific preset first, then the class-wide preset, before falling back to a legacy class config location or the activity center; the sign layer still rejects coordinates outside the published activity range. With `auto_answer`, it claims each new rapid-answer activity once through the same upstream answer boundary; both default off. and once for password/gesture activities only when that class has a nonempty preset sign code. It does not retry a failed activity; after a failed attempt, subsequent ticks only retry alert delivery. A slider-captcha challenge is solved automatically when a solver is configured and otherwise returns `CAPTCHA_REQUIRED` for the manual tool flow. QR activities alert with the scanned-payload requirement; the watcher leaves photo and face alert-only because their object IDs are operator-supplied. The explicit upload/photo/face tools support those flows behind separate scopes.

The daemon itself is also supervised across procd restarts. Before any listener starts it atomically writes a private 0600 marker; a SIGTERM shutdown rewrites that marker as clean, while an unexpected exit leaves it in the running state. The next process increments a persisted consecutive-crash counter, asynchronously sends a 30-second-bounded priority-9 notification (priority-10 from the third consecutive crash), and exposes only PID/timestamps/counters through `/healthz`. A clean shutdown breaks the crash chain but retains the last crash timestamp for diagnosis.

Every watcher cycle runs inside a supervision boundary. A panic is recovered, counted, logged and sent as a priority-9 notification; one successful cycle resets the consecutive-panic counter. Safe counters (`last_tick_at`, `last_panic_at`, `consecutive_panics`, `ticks`, `active_class_polls`) are exposed as an aggregate through unauthenticated `/healthz` and per account through the authenticated Web UI status. Polling also sleeps up to five minutes outside the configured window or when no watched schedule is active; the timer wakes at a window or class boundary so `lead_seconds` still applies. Course-group history is scanned only while at least one watched class is active, rather than all day. This removes the fixed one-minute, 24-hour request pattern on idle deployments.

`internal/notify` is deliberately provider-facing and stateless. Feishu posts one JSON text card, ntfy posts to the configured topic with priority 5, and Gotify posts to `/message` with an application token and priority 5. `Multi` tries every configured sender independently and joins the resulting errors; one provider failure does not suppress another channel. Each sender has a bounded request timeout, rejects provider error acknowledgements, and receives only a title and operator-facing body. Credentials and sign codes stay in private configuration and never enter watch state or notifications.

Watch state is a bounded JSON file in each account's private state directory. It stores activity identifiers, timestamps, result status and safe fault codes, not message bodies, sign codes or credentials. State replacement is atomic, and a malformed state file fails startup instead of resetting one-attempt bookkeeping. Class and group-feed failures are logged by safe fault code and do not stop the loop. The watcher is disabled unless `watch.enabled` is present and valid. The default account uses the top-level `watch` object; each tenant may define its own `watch` object and runs an independent loop with separate state and senders.

`get_activity_page` is the evidence-collection boundary for still-unverified classroom H5 flows such as type-42 practice. It accepts only an activity URL already present in the verified feed, follows that URL once, and returns the final URL, bounded text, iframe/script/link URLs, form actions and field names/types. Hidden values, cookies and raw page bytes are not exposed. This lets a real activity be captured for protocol reconstruction without advertising a guessed submission capability.

## Sign-in and device identity

Sign-in is split by responsibility. `internal/upstream` owns the class and course-group protocol chain, persistent Android-like device identity, account identity, automatic reauthentication and attendance verification. `internal/watch` owns course-time decisions and one-attempt-per-activity state. `internal/operation` owns the public contract, while `internal/authz` carries OAuth scopes from `internal/access` to `internal/mcphttp`. No adapter learns HTTP details and no watcher constructs URLs.

`internal/captchasolver` is a provider adapter, not part of the upstream protocol. The local detector receives the slider background/cutout pair and returns one coordinate without network access; DamaGou receives only the background. The daemon never exposes its userkey, endpoint, or raw model/provider errors. `internal/upstream` owns challenge state, image download, coordinate submission and the single retry.
The device state file persists a stable randomized `deviceCode`, Android-like identifiers, user agent and package name. The account-identity request encrypts a bounded device-info payload with the reference client's RSA public key and also decodes the returned `clientId` into the face-sign `cxcid`/`sc` pair. Location sign-in preserves query order and uses the reference client's small coordinate jitter plus one tightened retry after `errorLocation`. Password and gesture sign-in first verify the operator-provided code through the reference `checkSignCode` endpoint, then submit with the same ordered `stuSignajax` chain. QR sign-in parses the operator-scanned payload locally, verifies `signDetail`, and submits the QR `enc` without fetching the QR URL. Photo sign-in uses a pan object ID from the path-bounded upload tool. Face sign-in constructs the MD5 liveness result, exchanges it for `faceEnc`, and then submits; both remain behind distinct OAuth scopes.
Slider captcha uses the reference two-pass state machine. The first submission can return `validate_<enc2>`; the client stores that token in memory, returns `CAPTCHA_REQUIRED`, and exposes only image URLs through `get_sign_captcha`. `answer_sign_captcha` submits one operator-provided x-coordinate, stores the upstream validation token, and the next `sign_activity` adds `enc2` and `validate` in reference order. Raw challenge tokens are never returned, challenges expire in 10 minutes, and the watcher performs at most one solver-backed retry per configured sign attempt.

## Answer generation and work submission

`internal/upstream` discovers knowledge-point work cards and parses the editable question page, including the hidden submission form. It also bridges the global assignment entry: `get_assignment_questions` follows the signed `work/task` URL exactly once, accepts the upstream redirect to `work/dowork`, parses the same question/form model and caches that job for `answer_work`. Read-only `work/preview`, `work/prompt` and reviewed-work redirects return `WORK_UNAVAILABLE` instead of being treated as empty work. Work-job protocol parameters and parsed question sets are cached only in memory; `Enc`, `ktoken` and `cpi` are never returned through the tool contract. `internal/answer` owns external LLM/tiku providers, confidence thresholds, the local answer cache and question-type normalization. `internal/workdraft` owns the local draft file, validates a question ID against the current upstream question set before accepting an answer, and materializes both `pyFlag=1` save and final submit payload shapes. Drafts persist atomically in `<state_dir>/work-drafts.json` with mode 0600 and are bounded in size.

Upstream work mutation is intentionally isolated: the normal shared URL allowlist still blocks `addStudentWorkNew`, and only `SubmitWorkPayload` may call that exact endpoint. `save_work` requires at least one draft; `submit_work` requires every parsed question to have a draft. Learning progress, logging and arbitrary task mutation routes remain blocked.
