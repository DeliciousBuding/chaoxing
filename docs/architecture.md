# Architecture

Chaoxing runs as one Go binary. `serve` owns one upstream client, authenticated cookie jar and cache per account, and exposes two loopback listeners. The public listener serves the management Web UI, OAuth and MCP; the private listener serves local bearer-token calls. Local CLI clients use the default account's daemon session rather than create a fresh upstream client each time.

```text
Browser member  -> HTTPS mcp.example.com -> Cloudflare Tunnel
                                      -> 127.0.0.1:8792 -> Web UI session -> /api tools
MCP client      -> HTTPS mcp.example.com -> Cloudflare Tunnel
                                      -> 127.0.0.1:8792 -> owner OAuth -> MCP tools
Local CLI client -> chaoxing call
                                      -> 127.0.0.1:8793 -> local bearer -> same tools
                                                                         |
                                                        bounded upstream client
                                                                         |
                                                              Chaoxing over HTTPS
```

Only port 8792 enters the tunnel. Port 8793 is private to the host; it carries authenticated local calls, not public OAuth or browser traffic. `configure` writes private installation state. `query` directly uses the upstream client and is useful for isolated diagnostics; it should not run concurrently against state owned by `serve`.

Several optional layers are off by default. An egress pool (`internal/egress`) routes upstream traffic through configured SOCKS5 endpoints with account-sticky selection, transport-failure cooldown and a direct fallback while the selected endpoint cools; it learns health only from real request outcomes and never probes in the background. An account assignment is stable across restarts and is removed only when that endpoint is no longer configured. `internal/statestore` always persists the private per-account sign-in audit, and, when their features are enabled, endpoint health, sticky assignments, sanitized captures and per-account BD-09 location presets/bindings in SQLite. Additional accounts mount under `/t/<id>/` with independent sealed credentials, cookie jars, caches, query queues and OAuth state. The process-wide transport pool, endpoint-health database and outbound budget are deliberately shared; they contain no account session or coursework credentials. This is logical account isolation within one trusted process, not process or network-egress isolation.

Upstream requests also pass a per-account pacing boundary. The default minimum interval is 650 ms with 35% random jitter; redirects and retries use the same boundary. Shared HTTP transports enable HTTP/2, keep at most two idle connections per host, and let Go's transport negotiate gzip automatically when the upstream supports it. The watcher adds randomized 750 ms–3 s gaps between class polls and 5–25 s before automatic sign-in. These values are risk controls, not throughput controls.

## Owner Web UI

`internal/webui` embeds the production Vite bundle from `web/src` and mounts it at `/` and `/app`. Platform login is separate from MCP OAuth: the owner account is seeded from the deployment PBKDF2-SHA256 hash, additional members live in `control.db`, and a successful login issues a random opaque session ID that exists only as a SHA-256 key in memory. The cookie uses the `__Host-` prefix, `Secure`, `HttpOnly`, `SameSite=Strict`, an eight-hour absolute TTL and a thirty-minute idle TTL. The in-memory session is bound to the originating client network: IPv4 `/24` and IPv6 `/64`. This tolerates small mobile-network changes while bounding cross-network cookie theft. All browser API requests must carry the configured Host; a different Host is rejected before authentication. Only trusted reverse proxies may supply the client address. The default trust set is loopback only; `X-Forwarded-For` is read right-to-left from the first non-trusted address, so a direct client cannot forge its leftmost value. Login prunes expired sessions and caps active sessions at 32, with six sessions per platform identity. Owner/admin logins can replace their own oldest session; an owner login may evict the lowest-privilege session, so viewer bursts cannot lock out the owner. A handler re-checks the live session record after authentication; a deleted or missing record is a hard 401, never a zero-value owner session. Every state-changing API request requires both the cookie and an `X-Chaoxing-CSRF` header matching a separate CSRF cookie. Login attempts are bounded per client network to five per minute and twenty per fifteen minutes. The authenticated dashboard exposes safe egress, process and watcher counters; public `/healthz` is liveness-only and `/readyz` exposes stale/degraded/panic/tick/audit state. Immutable embedded assets are served with strong content-hash ETags, `Vary: Accept-Encoding`, immutable cache policy and precompressed gzip representations. The embedded console is a compact Linear-inspired dark-first design system with dark and light themes, solid surfaces, a fixed responsive sidebar and no external animation or resizable-layout runtime; all controls are same-origin and the optional Baidu map remains an isolated sandboxed document.

The UI API has no parallel capability definition. `/api/tools/call` only accepts names from `internal/operation`, and execution is dispatched to the selected root or tenant account executor. API bodies are capped at 128 KiB, tool calls receive a ninety-second context, and errors use safe fault codes. The static bundle has a strict CSP, `nosniff`, no-referrer, HSTS, a restrictive `Permissions-Policy`, `Cross-Origin-Opener-Policy: same-origin`, `frame-ancestors 'none'`, and immutable caching for hashed assets. The bundle contains no analytics or tracker. Its connections are same-origin only. The optional Baidu map is a separate `/map` document with `sandbox="allow-scripts"` (opaque origin); it receives only an AK and selected coordinates over `postMessage`, and its broader map CSP cannot access the parent session or CSRF token. Map geocoding calls remain server-proxied and bounded.

The UI intentionally does not expose arbitrary file browsing, shell execution, URL fetching, raw cookies, hidden form values or upstream HTML. Dangerous operations such as final submission and sign-in remain explicit button actions with confirmation.

## Control plane and tenant scope

The control plane models only three things: a platform member who can log in, an upstream account (tenant) that owns one Chaoxing identity and state directory, and an explicit grant saying that a member may use an account. `control.db` contains `admin_users`, `account_grants` and `audit_events`; tenant `chaoxing.db` continues to contain sign-in evidence, captures, location presets and proxy state. No credential, cookie, coordinate or coursework body crosses into `control.db`.

| Role | Member management | Account scope | Tool capability |
| --- | --- | --- | --- |
| owner | All; unique super-admin | All | All |
| admin | Operators/viewers; can modify self only | All | All |
| operator | None | Explicit grants | Read, sign, work, answer, upload |
| viewer | None | Explicit grants | Read only; no capture or sign-in address/IP audit |

Roles are fixed capability presets, not a general permission DSL. Owner may grant `admin`; admin cannot create or modify another admin, and no session can change its own role or status. A password, role, status or grant change increments `auth_version`; the next authenticated request re-reads the member and rejects a stale session. The owner username and password remain deployment-managed because the same password hash protects OAuth consent; editing the private config and restarting reconciles them onto the existing owner record without forking the two authentication paths.

Control-plane audit records login success/failure, logout, account selection, member and grant changes, tool calls, permission denials and private location preset/binding writes. WebUI tool calls are audited by the browser boundary; root MCP calls, tenant MCP calls and loopback `/call` are audited by the daemon executor wrapper, with OAuth client fingerprint or `local` as actor. Tool arguments, passwords, tokens, cookies, question bodies and page text are deliberately excluded. Details are field-whitelisted, bounded to 4 KiB and retained for 180 days; pruning runs at startup, and audit-write failures increment readiness/status counters. Tenant sign-in audit remains the authoritative evidence for submitted address, coordinates and egress IP.

## Production activity capture

Watcher capture is an evidence layer for still-unverified classroom H5 protocols, especially practice/type-42 flows. Each observation is deduplicated by account and `course:class:activity`, and stores activity identity, state, first/last-seen timestamps, update count and sanitized JSON projections. A practice page can be fetched once through `get_activity_page`; page evidence is never overwritten. The Web UI lists captures without page payloads and fetches sanitized page JSON only through an explicit opt-in query. The store rejects oversized payloads, omits hidden values, cookies, credentials and raw bodies, and prunes entries after a configurable retention period (default seven days). Capture failures do not interrupt watcher operation.

## Concurrency and resource budgets

The smallest stateful unit is an account. Its upstream operations are serialized because login, cookie snapshots and caches mutate together. Allowing concurrent reads against those structures would require a larger state redesign and could produce redundant logins or lost cookie updates. Different accounts can progress independently. Capability discovery does not access account state and bypasses the account queue.

| Boundary | Active / waiting | Saturation behavior |
| --- | --- | --- |
| Account operations, shared by CLI and MCP | 1 / 8 per account | Immediate `RATE_LIMITED` once all nine places are occupied; waiting respects caller cancellation |
| Process-wide outbound HTTP, all accounts | 4 / 32 | Bounded admission, with capacity held through body EOF or close; failures and cancellation release capacity |
| Public MCP transport, per endpoint | 4 / 0 | HTTP 503 with `Retry-After`; this protects request parsing, not account state |

Local calls have a 90-second total budget; MCP tools have 30 seconds. Account and outbound waits consume that same budget, not a fresh timeout per stage. The shared gate has no worker goroutines or polling. Account waiters acquire no outbound slot until they actually issue HTTP, so one busy account cannot reserve the process-wide budget while idle in its queue. There is no strict weighted fairness guarantee. All-tenant overload remains bounded, not unlimited goroutine accumulation inside business queues.

The HTTP transport is shared, not the cookie jar. Raw reads retain the same allowlisted paths and bounded response sizes. Caller cancellation is not classified as a failing proxy. Endpoint persistence is serialized per endpoint but happens outside the pool selection/status mutex; slow SQLite cannot hold that global lock. A persistence error keeps in-memory health usable and sets `persistence_degraded` in private management status.

## SQLite scope and durability

SQLite stores the private sign-in audit (submitted address/coordinates, observed egress IP, method and result), non-authoritative endpoint health, sticky egress assignments, sanitized activity captures and private BD-09 location presets/course bindings—not accounts, assignments, tokens or cookies. One reusable connection serializes short indexed upserts and deletes. This workload does not justify separate reader pools, sharding, a write-behind queue or another service. Healthy rows are deleted; normal requests that do not change health do not write. Replaced endpoints can leave stale rows, which are ignored unless their exact endpoint key is configured again.

Tenant `chaoxing.db` uses WAL with `synchronous=NORMAL`, a one-second busy timeout, a two-second operation context and a bounded two-megabyte page cache (`cache_size=-2048`). Automatic checkpointing starts at 256 pages; `journal_size_limit=4 MiB` limits retained journal size after resets, not an absolute WAL file-size cap. Schema creation, shape validation and `user_version` update commit atomically. Schema v4 adds proxy assignments, activity captures and location tables; older databases migrate in place and no OAuth reauthorization is required. NORMAL can lose recent health/capture updates on power failure; this is acceptable for reconstructible operational evidence. The authorization-bearing `control.db` uses `synchronous=FULL` instead.

The DB is created/chmodded to 0600 before sidecars, database symlinks are rejected, and filenames are URI-escaped. Existing parent permissions and trusted exclusive ownership still matter. Keep one daemon per store on a local filesystem. Do not copy a live WAL main file as a consistent backup; use SQLite's backup API or stop the owner first. Benchmarks in `internal/statestore` are synthetic local-write measurements, not upstream throughput or deployment capacity claims.

## Authentication boundaries

Public DCR registrations last 90 days so connector setup retries can reuse their cached client IDs. Registration alone grants no permission: every authorization requires owner login and consent. The pool is capped at 128 and reclaims the oldest unapproved registration first at capacity; approved registrations are not evicted by anonymous registrations. Login/consent challenges still expire after 10 minutes and authorization codes after 60 seconds.

The public owner authorization layer supports seven OAuth scopes: `chaoxing.read` for course reads, `chaoxing.sign` for sign-in, `chaoxing.work` for local draft edits, `chaoxing.answer` for generated answers and rapid-answer participation, `chaoxing.work.submit` for upstream work save/submit, `chaoxing.upload` for pan uploads, and `chaoxing.face` for face enrollment/signing. Its password uses a salted PBKDF2-SHA256 hash with 600,000 iterations. This owner credential is separate from the upstream credential, which must be recoverable for automatic login. Use different passwords. Registration records the requested scope, authorization requires explicit owner consent, refresh can narrow but never widen it, and the MCP adapter checks the required scope before contacting upstream or opening the draft store.

Authorization codes expire after 60 seconds and use S256 PKCE. Random opaque access tokens last 15 minutes; refresh families have a 30-day lifetime. Refresh rotation preserves the original expiry. Issuer-bound MAC proofs authenticate family/counter/nonce values so old replay can revoke a family without retaining every historical token. State stores only active digests and one bounded record per family. The authorization server is database-free and does not issue JWTs or publish JWKS. DCR is the default registration flow; optional CIMD requires explicit opt-in and external metadata reachability.

The upstream client implements the upstream AES login protocol over HTTPS. Its GET helper detects login responses, reauthenticates once and retries once. A second login rejection returns `AUTH_REQUIRED`; notices and schedules have their own POST rejection handling after establishing a session with a read. This is not an unlimited retry loop or a verification bypass.

AES-GCM protects upstream credentials and persisted cookies with separate authenticated purposes. A separately stored key is required for unattended operation. Restrict the key and state to the service's trusted identity (root-only for a root-run installation). Root and a compromised service process can recover the credentials; file encryption does not defeat those actors.

## Data boundaries

`internal/operation` is the single transport-independent capability registry. It declares stable operation IDs, legacy MCP names, argument bounds, schemas and descriptions. CLI, daemon and MCP use the same validator and additive result metadata. Business commands call the daemon rather than create another authenticated client. No adapter executes another adapter as a subprocess.

`chaoxing capabilities` and `chaoxing schema assignments.list` work without credentials. `get_capabilities` advertises verified operations and explicitly unsupported domains. The registry is hand-curated from verified behavior, not generated from a claimed official upstream OpenAPI specification.

`meta.status` describes source coverage, not whether homework is finished. Coverage is independent of output pagination. Unknown submission states are never classified as submitted. Aggregation is bounded and retains source failures; notification prose is untrusted data, not instructions or automatically inferred assignments.

Tools read coursework, generate answers, submit explicitly allowlisted sign-in/answer/work/upload actions, or edit local answer drafts. Login and token issuance change authentication state; sign-in changes attendance state and therefore requires `chaoxing.sign`; answer generation/participation requires `chaoxing.answer`; draft mutation changes only local draft state and requires `chaoxing.work` (therefore `answer_work` requires both); upstream work mutation requires `chaoxing.work.submit`; upload requires `chaoxing.upload`; face state requires `chaoxing.face`, and face sign also requires `chaoxing.sign`. Tool allowlisting is enforced at the interfaces; clients do not supply arbitrary upstream URLs or remote commands.

Without a course filter, assignment enumeration uses the incomplete global feed. A course-name query enumerates matching enrolled classes, obtains work-list signatures, pages each class's work list and checks unique rows against upstream totals. `complete: true` is scoped to those matched classes and requires every scan to agree with its total. Output pagination and status filtering then slice the fetched source. Consumers must retain `complete`, `coverage` and timestamp fields. [Tool contracts](tools.md) describes bounds and remaining limits.

The MCP callback has a shared 30-second context. Sequential scans across multiple matching classes may exhaust it before completing; use a narrower course name when possible.

## Optional activity watcher

`internal/watch` is an opt-in background loop inside `serve`. Activity reads share the account queue and bounded outbound budget; alerts use `internal/notify`. Per-class schedules and a global window bound discovery. Course-group cards supplement the class feed when enabled. With `auto_sign`, normal/location cards enter the upstream sign-in state machine; password/gesture cards also require the class's operator-provided sign code. Location resolution uses a schedule-specific binding, class binding, configured location or activity center, and the signer rejects coordinates outside the published range. Transient sign failures have at most four attempts with backoff; capacity and upstream cooldown waits do not consume that budget. Terminal failures need manual handling. Notification retry never repeats a successful submission. `auto_answer` separately controls rapid-answer claims. Both switches default off. A configured solver may handle one slider challenge per sign attempt; otherwise the captcha needs operator input. QR/photo/face stay alert-only in the watcher and require explicit tool inputs and scopes.

An accepted sign-in whose attendance read fails remains in the private watch state as `verify`, with its activity and submission receipt. The watcher performs only independent attendance reads, including after the activity disappears, its class window ends or the process restarts. At most two receipts are checked per tick; actual verification failures have four attempts, cooldown waits retain their retry deadline, and receipts expire after 24 hours. This deadline can wake the loop outside discovery windows. A confirmed result is persisted before notification; failed pushes retry delivery, never submission. CLI/MCP expose the same read-only confirmation through `get_sign_status`. `SIGN_VERIFICATION_PENDING` tells callers to wait for confirmation rather than submit again.

Interactive submission uses an owned class card cached for at most 30 seconds or an owned group card read within one minute before it considers fetching the class feed. The watcher also persists already-discovered active observations, without raw URLs or feed ext material, so eligible retries and restart recovery do not depend on that short list cache. Internal observed actions validate matching activity/course/class, enrollment, freshness and deadline, then use fresh authoritative details and `preSign`; they do not clear or bypass any endpoint cooldown. Observations are bounded by their end time and 24 hours, or ten minutes without an end time. An already-signed response remains external/prior attendance, not a newly completed automatic submission.

Every active class poll logs class, start/completion timestamps, duration, status, item count, retry delay and up to eight `activity_id:user_state:raw_user_status:signable` observations. A class-list `userStatus` is an unverified hint, not an attendance receipt: sign-in cards expose `user_state=unknown` and `state_source=class_feed_unverified`. An active card remains a sign-in candidate regardless of that hint. The signer checks the actual `preSign` page and verifies the result through the separate attendance endpoint. Only statuses 1, 2, 3 and 9 confirm attendance; absence, leave and unknown codes do not. A result with `method=none` and `submitted=false` means attendance was confirmed without a submission in this attempt. Notifications distinguish this from an automatic submission.

Each account retains private `protocol-evidence.jsonl` records beside its sealed session. Requests to activity, sign-detail, pre-sign, analysis, submission and attendance endpoints record method, endpoint path, activity identifiers, timestamps, upstream Date, duration, HTTP status, body size/hash and an allowlisted response projection. A sign-attempt identifier connects requests to the final `submitted`/`verified` outcome. `submitted` records that a submission request was attempted; it does not mean the request was accepted. Actual requests and cooldown-deferred reads are distinct. No full response body, query string, cookie, name, coordinate or challenge token is retained. Records are at most 8 KiB; 2 MiB segments retain at most three predecessors, with old segments removed after seven days. Files are 0600 in the private account directory. Three consecutive default-account evidence-write failures degrade readiness.

Upstream HTTP 429 and the business response `请勿频繁操作` are `UPSTREAM_RATE_LIMITED`, not parser failures. Local account/endpoint recovery probes back off through 60 seconds, 2 minutes, 5 minutes, 15 minutes and one hour. A valid upstream `Retry-After` (seconds or HTTP date, up to 24 hours) takes precedence when longer; `retry_after_source` distinguishes the dominant local versus upstream wait in safe faults and protocol evidence. Reads and writes share the boundary; cooldown sends no request. Private 0600 state is atomically persisted and restored before account requests. Waiting/restart never resets history; an accepted endpoint response does. Invalid state fails startup. The loopback API returns HTTP 429 with `Retry-After`.

Sign-in discovery notifications do not use the actionability filter. Signed, finished, unknown and unsupported cards get a separate persistent discovery receipt; finished cards are labeled historical and never submitted. Active cards have priority over historical messages in the bounded outbox. Discovery delivery does not overwrite submission/verification state, and result delivery does not erase an outstanding discovery message. The first discovery failure warns immediately once per failure episode. A short remaining window removes discretionary delay, while a required retry wait crossing the deadline produces a manual-action alert, not an early request. Idle maintenance wakes do not accelerate active-class polling.

Successful class activity lists have a shared, per-class 30-second cache used by the watcher, interactive reads and sign preflight. Coverage details expose each class's cache hit and original fetch time. Failed reads are not cached, expired data is not served, and a known cooldown is never hidden by cached success. Deferred activity queries return before course or group lookups; a query whose entire class source fails does not continue with group reads before returning the failure. List state remains unverified regardless of cache freshness. Poll intervals and pacing are operational request budgets, not claimed platform rate-limit thresholds.

The daemon itself is also supervised across procd restarts. Before any listener starts it atomically writes a private 0600 marker; a SIGTERM shutdown rewrites that marker as clean, while an unexpected exit leaves it in the running state. The next process increments a persisted consecutive-crash counter, asynchronously sends a priority-9 notification (priority-10 from the third consecutive crash) with three bounded retries, and exposes only PID/timestamps/counters through `/healthz`. A clean shutdown breaks the crash chain but retains the last crash timestamp for diagnosis. Corrupt or unwritable markers degrade to in-memory counters rather than blocking startup. Alarm delivery uses a shared transport with a 20-second TLS-handshake ceiling and retries transient failures three times; ordinary activity alerts keep one attempt because the watcher re-sends them on the next tick.

Operators configure private coordinates through `chaoxing location` on the deployment host rather than through MCP or the browser API. The command writes to the same per-account SQLite store the watcher resolves against; no coordinate or building label is accepted by an agent-facing tool, and none is persisted in the repository. `/readyz` reports `stale` when a live watcher has not completed a cycle for fifteen minutes, which is three times the five-minute idle sleep cap and therefore only fires when the loop is wedged.

Every watcher cycle runs inside a supervision boundary. A panic is recovered, counted, logged and sent as a priority-9 notification; one successful cycle resets the consecutive-panic counter. Safe counters (`last_tick_at`, `last_panic_at`, `consecutive_panics`, `ticks`, `active_class_polls`) are exposed per account through the authenticated Web UI and loopback management status, while `/readyz` exposes only aggregate readiness. The first poll runs immediately on start and then sleeps up to five minutes outside the configured window or when no watched schedule is active; the timer wakes at a window or class boundary so the configured 20-minute before/after padding still applies. Schedule entries carry independent stable keys, teaching-week ranges and room metadata, so a guidance class can bind a different private location preset. Course-group history is scanned only while at least one watched class is active, rather than all day. This removes the fixed one-minute, 24-hour request pattern on idle deployments. Ticks are serialized, bounded by a 90-second context, and one process holds the state-directory lock.

`internal/notify` is deliberately provider-facing and stateless. Feishu posts one JSON text card; ntfy and Gotify carry watcher-supplied priority (9 for scheduled classroom events, 6 for ordinary assignments outside class). Urgency follows the exact course/class schedule, not the upstream activity-versus-assignment endpoint. Both feeds run each classroom tick; idle assignment scans retain the five-minute per-class bound. Ticks remain serialized with a five-second minimum configured interval and no catch-up bursts after slow work. `Multi` tries every configured sender independently and joins the resulting errors; one provider failure does not suppress another channel. Each sender has a bounded request timeout and rejects provider error acknowledgements. Credentials and sign codes stay in private configuration and never enter watch state or notifications.

Watch state is a bounded JSON file in each account's private state directory. It records activity identifiers, timestamps, safe fault codes, attendance verification and submission attribution. Older success entries without attendance proof are rechecked before suppression. Replacement is atomic; corrupt state is quarantined and degrades readiness. Class and group-feed failures do not stop the loop. The watcher is disabled unless `watch.enabled` is valid; tenants have independent state and senders.

`get_activity_page` is the evidence-collection boundary for still-unverified classroom H5 flows such as type-42 practice. It accepts only an activity URL already present in the verified feed, follows that URL once, and returns the final URL, bounded text, iframe/script/link URLs, form actions and field names/types. Hidden values, cookies and raw page bytes are not exposed. This lets a real activity be captured for protocol reconstruction without advertising a guessed submission capability.

## Sign-in and device identity

[Sign-in protocol](signin-protocol.md) records the pinned reference comparison, supported request variants and deliberate differences. Participation requests use the person ID (`puid`); IM authentication keeps the separate user ID. An exact pre-sign 403 can recover the session once, while other HTTP rejections retain their normal fault classification. QR payloads cannot redirect an operation to a different activity. Submitted-location audits come from the constructed request rather than unused caller defaults.

Sign-in is split by responsibility. `internal/upstream` owns the class and course-group protocol chain, persistent Android-like device identity, account identity, automatic reauthentication and attendance verification. `internal/watch` owns course-time decisions and one-attempt-per-activity state. `internal/operation` owns the public contract, while `internal/authz` carries OAuth scopes from `internal/access` to `internal/mcphttp`. No adapter learns HTTP details and no watcher constructs URLs.

`internal/captchasolver` is a provider adapter, not part of the upstream protocol. The local detector receives the slider background/cutout pair and returns one coordinate without network access; DamaGou receives only the background. The daemon never exposes its userkey, endpoint, or raw model/provider errors. `internal/upstream` owns challenge state, image download, coordinate submission and the single retry.
The device state file persists a stable randomized `deviceCode`, Android-like identifiers, user agent and package name. The account-identity request encrypts a bounded device-info payload with the reference client's RSA public key and also decodes the returned `clientId` into the face-sign `cxcid`/`sc` pair. Location sign-in preserves query order and uses the reference client's small coordinate jitter plus one tightened retry after `errorLocation`. Password and gesture sign-in first verify the operator-provided code through the reference `checkSignCode` endpoint, then submit with the same ordered `stuSignajax` chain. QR sign-in parses the operator-scanned payload locally, verifies `signDetail`, and submits the QR `enc` without fetching the QR URL. Photo sign-in uses a pan object ID from the path-bounded upload tool. Face sign-in constructs the MD5 liveness result, exchanges it for `faceEnc`, and then submits; both remain behind distinct OAuth scopes.
Slider captcha uses the reference two-pass state machine. The first submission can return `validate_<enc2>`; the client stores that token in memory, returns `CAPTCHA_REQUIRED`, and exposes only image URLs through `get_sign_captcha`. `answer_sign_captcha` submits one operator-provided x-coordinate, stores the upstream validation token, and the next `sign_activity` adds `enc2` and `validate` in reference order. Raw challenge tokens are never returned, challenges expire in 10 minutes, and the watcher performs at most one solver-backed retry per configured sign attempt.

## Answer generation and work submission

`internal/upstream` discovers knowledge-point work cards and parses the editable question page, including the hidden submission form. It also bridges the global assignment entry: `get_assignment_questions` follows the signed `work/task` URL exactly once, accepts the upstream redirect to `work/dowork`, parses the same question/form model and caches that job for `answer_work`. Read-only `work/preview`, `work/prompt` and reviewed-work redirects return `WORK_UNAVAILABLE` instead of being treated as empty work. Work-job protocol parameters and parsed question sets are cached only in memory; public question results withhold `Enc`, `ktoken`, `cpi` and similar session-bound form values, listing their names in `redacted_form_fields`. The local draft exporter is the only path that reads the cached full form. `internal/answer` owns external LLM/tiku providers, confidence thresholds, the local answer cache and question-type normalization. `internal/workdraft` owns the local draft file, validates a question ID against the current upstream question set before accepting an answer, and materializes both `pyFlag=1` save and final submit payload shapes. Drafts persist atomically in `<state_dir>/work-drafts.json` with mode 0600 and are bounded in size.

Upstream work mutation is intentionally isolated: the normal shared URL allowlist still blocks `addStudentWorkNew`, and only `SubmitWorkPayload` may call that exact endpoint. `save_work` requires at least one draft; `submit_work` requires every parsed question to have a draft. Learning progress, logging and arbitrary task mutation routes remain blocked.
